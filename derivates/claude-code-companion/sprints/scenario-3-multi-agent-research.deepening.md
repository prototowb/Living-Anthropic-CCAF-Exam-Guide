# Scenario 3 — Deepening pass

> Addendum to scenario-3-multi-agent-research.md. Reviewed against Task Statements 1.1, 1.2, 1.3, 1.4, 1.6, 1.7, 5.1, 5.3.

## Architect mandates we are honouring

- **TS 1.2 — Hub-and-spoke with coordinator-mediated routing.** `tutor/coordinator.ts:22-29` asserts `Task` in `ALLOWED_TOOLS` at module load; spokes never call each other; the merge happens in `coordinator.handle`. Matches the "all inter-subagent communication through the coordinator" knowledge item.
- **TS 1.2 — Dynamic subagent selection.** `classifyIntent` (`coordinator.ts:40-64`) returns a *subset* keyed on the prompt, not a fixed pipeline. Few-shot example 1 (`fewShot.ts:14-18`) demonstrates the single-spoke choice; example 3 the multi-spoke parallel choice.
- **TS 1.3 — `Task` in allowedTools + explicit context passing.** Each spoke receives the full prompt in its own `createMessage` call (`explainer.ts:11-15`); no implicit inheritance. Parallel spawn via `Promise.all` (`coordinator.ts:81`) honours the "single coordinator response, multiple Task calls" skill.
- **TS 4.3 (adjacent) / TS 1.2 — Quality criteria over procedural steps.** `SYSTEM_PROMPT` (`fewShot.ts:38-56`) describes *goals* ("decide which subagents", "independent MUST be parallel", "prefer fewer") rather than a script.
- **TS 5.1 — Pruner + scratchpad.** Every turn passes `inv.toolCalls` through `prune` (`coordinator.ts:85-91`) and writes a one-line finding to `tutorScratchpad` (`coordinator.ts:97-99`). The 8-line scratchpad summary survives turn boundaries.
- **TS 5.3 (partial) — Capabilities-aware degradation.** `canParallel` branch (`coordinator.ts:77-82`) avoids silently failing on small local models; serial fallback is explicit.

## Architect mandates we are NOT yet honouring (gaps)

- **TS 1.2 — Iterative refinement loop.** Skill item: *"the coordinator evaluates synthesis output for gaps, re-delegates to search and analysis subagents with targeted queries, and re-invokes synthesis until coverage is sufficient."* Our `handle()` is single-shot — one classify, one dispatch, merge, done. No coverage check, no re-delegation. **New task (v0.3):** `evaluateCoverage(invocations, originalPrompt)` returns `{ coveredGoals: string[]; gaps: string[] }`; if non-empty, re-dispatch a targeted second round (capped at one extra round) before merging. Wires `docSynthesiser` (v0.2 task 2) into the loop.
- **TS 1.4 — Programmatic prerequisite enforcement.** v0.4 task 13's "lint script forbidding store imports" is the right idea but there is no *runtime* gate on workflow ordering. The `docSynthesiser` (v0.2 task 2) takes other spokes' outputs as input — if the coordinator dispatches it before `explainer`/`codebaseResearcher` complete, output is empty. Prompt-level "wait for inputs" is the anti-pattern the mandate names. **New task (v0.2):** declare a `dependsOn?: TutorSubagentName[]` field on each spoke; the coordinator partitions the dispatch list into a DAG and only `Promise.all`-bundles within the same layer. Hard runtime error if a spoke runs without its declared inputs.
- **TS 1.6 — Adaptive vs fixed decomposition is undocumented.** The plan implies the classifier picks spokes, but the *strategy* is not articulated. Today this is fixed (intent → spoke set, no replanning). **New task (v0.3):** capture the choice in `prompts/decompositionStrategy.ts` — small enum + few-shot showing when adaptive replan fires (used by the iterative loop above) vs fixed parallel dispatch.
- **TS 1.7 — Session resumption / forking.** v0.2 task 4 persists the thread to `localStorage`, but there is no *named session* model, no `forkSession`, no resume-with-summary path. The exam guide is explicit about both. **New task (v0.3):** introduce `tutorStore.sessions: Record<sessionId, Thread>`, a "fork from here" button at any turn that branches state into a new sessionId, and "resume with summary" that injects `tutorScratchpad.summarize()` at the head of the resumed thread instead of replaying every message.
- **TS 1.7 — Stale-results awareness on resume.** If the user edits a lesson body between sessions and resumes, the prior researcher citations are stale. **New task (v0.4):** stamp each `SubagentInvocation` with the source hash it read from; on resume, flag invocations whose source has changed and offer a one-click re-run.
- **TS 5.1 — Structured "case facts" outside summarised history.** Today's scratchpad is one-line free-text findings. Mandate names extracting *structured* facts (stage ids, lesson ids, weak spots) into a persistent layer. Today these are buried in prose. **New task (v0.3):** add `tutorScratchpad.facts: Record<string, unknown>` set by spokes (`recordFact('weakStage', 'S2')`) and injected into every subsequent classifier prompt as a structured block above the user message — *not* inside the summarised list.
- **TS 5.1 — Subagents return structured outputs, not prose.** Our spokes return `output: string` (`explainer.ts:18`). Downstream merge is `.join('\n\n---\n\n')`. The mandate explicitly says to return key facts + citations + relevance scores, not verbose prose. **New task (v0.3):** widen `SubagentInvocation` with `findings: Array<{ claim; citation?; confidence }>` so `docSynthesiser` consumes structured input. The string `output` becomes a render of `findings`, not the source of truth.
- **TS 5.3 — Structured error propagation.** Today a spoke that throws will reject the `Promise.all` and the whole turn fails — the anti-pattern the mandate names ("terminating entire workflows on single failures"). No try/catch around the dispatch. No distinction between transient/business spoke failure. No `coverage annotations` in the merged reply. **New task (v0.2, urgent):** wrap each spoke in `Promise.allSettled` semantics; on rejection record `{ name; failureType; attempted; partial; alternatives }` into the `SubagentInvocation`; coordinator continues with the partial set and annotates the merged reply ("`codebase-researcher` was unavailable — answer below covers concept only"). This is the canonical TS 5.3 demonstration and v0.1 ducks it.

## Liftable patterns from the parent project

Worth lifting:

- **Confidence-fed escalation hook on the coordinator.** Parent `coordinator.ts:84-88` runs `shouldEscalate` (from `escalation.ts`) on every turn and threads the result into the reply. Our `tutor/coordinator.ts` has no escalation path — a low-confidence intent classification (line 62-64 in our file already returns `confidence: 0.4`) silently dispatches to the explainer instead of asking for clarification. **Lift:** import `shouldEscalate` from `src/agents/escalation.ts` (Scenario 1 shared module) and surface a "Tutor isn't sure what you meant" affordance when `low_confidence` fires.
- **The `*Spec` tool-descriptor pattern** (Scenario 1 deepening calls this out, applies here too). The Tutor's spokes have no machine-readable descriptions — when v0.3 task 6 (Scenario 4) flips to native tool dispatch, the model has nothing to read. Lift the `*Spec` convention from `src/agents/tools/searchPatterns.ts` to each spoke.
- **`coordinator.ts:35-38` `CoordinatorContext` parameter.** The parent threads `consecutiveBusinessErrors` and `userAskedForHuman` through `handle()`. Our `tutor.handle(prompt)` accepts no context — meaning the iterative-refinement loop above cannot pass "you already tried these spokes" to the next round. Lift the context-parameter pattern.

Not worth lifting:

- Parent has no fork/resume either — TS 1.7 is a gap shared with the parent. We get to lead.
- Parent's `batches.ts` and `modes.ts` belong to Scenario 5 and 2; not relevant here.

## Efficiency wins (shared with other scenarios)

- **Iterative-refinement loop is a Scenario 3 + 6 joint primitive.** Scenario 6's pipeline also needs a "validate → re-prompt → re-validate" loop (their v0.2 task 4 validator currently exits 1 on bad output). Define one `iterateUntil(predicate, opts)` helper in `src/agents/iterate.ts` consumed by both. Single landing point.
- **`Promise.allSettled` error-propagation pattern is a Scenario 1 + 3 + 4 joint move.** Scenario 1 helpBot has no parallel dispatch yet; Scenario 4 v0.3 task 6 adds tool dispatch which can fail mid-sequence. Define `dispatchAllSettled(invocations)` once in `src/agents/dispatch.ts`, returning `{ ok, errors, partial }`. Both helpBot and the Tutor consume the same helper. Scenario 1's deepening pass already widens `ToolResponse` with `{ attempted; partial; alternatives }` — match that exact shape so the dispatcher can lift fields without translation.
- **Structured-findings shape (`Array<{ claim; citation; confidence }>`) is Scenario 3 + 4 + 6.** Scenario 4's citations (v0.2 task 4) and Scenario 6's `citation.ts` schema (v0.4 task 9) describe the same thing. Define `Finding` and `Citation` once in `src/agents/schemas/findings.ts`; the codebase-researcher emits them, `docSynthesiser` consumes them, the content pipeline validates them.
- **"Limited" badge shared with Scenario 1.** Existing plan calls this out (v0.3 task 8); confirm. Concretely: `src/components/AdapterCapabilityBadge.vue` with a `capabilities` prop. Both `/tutor` and the `HelpBotSidebar` mount it.
- **Curriculum bridge (`src/agents/tutor/curriculum.ts`, v0.3 task 9) — helpBot can absolutely use it too.** HelpBot v0.2 task 1 (`lookupQuizAttempts`) and task 2 (`recordWeakSpot`) both need the same readonly accessor. Move it up the tree to `src/agents/curriculum.ts` (drop the `tutor/` namespace) so both coordinators import from one place; the rule against agent→store imports stays intact because the bridge *is* the abstraction layer.
- **Scratchpad needs eviction.** Existing plan (Risks §3) says "bound to ~50 entries"; do this in `src/agents/scratchpad.ts` with a `MAX_ENTRIES = 50` constant + ring-buffer behaviour. Shared with helpBot scratchpad — same primitive, same fix.
- **JSON-in-prose fallback parser (existing v0.3 task 7) → factor to `src/agents/schemas/parse.ts`** as Scenario 6's deepening expects. Single `extractFirstJsonObject(text)` consumed by Tutor classifier, helpBot dispatcher (Scenario 1), and the extraction pipeline (Scenario 6).
